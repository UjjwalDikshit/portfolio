Full-Stack Coding Platform

Pinned on GitHub · MERN + Redis + Judge0

Problem (how I’d explain it to you)

Every submission fans out to auth, persistence, and a sandbox (Judge0). If I naïvely hit the DB on every session check and every repeat read, and block the UI on every judge call, the system falls over when users pile in.

Why I didn’t stop at “CRUD + calls”

I needed cache-aware session validation, a hard boundary around execution so one slow sandbox doesn’t wreck the whole UX, and an admin surface so we’re not editing production data by hand.

What I implemented

  • JWT + Redis for session semantics: short-lived access pattern with cache-friendly session lookups.
  • Redis caching on read-heavy API surfaces; invalidate on writes that matter.
  • Judge0 as isolated execution plane; API layer handles orchestration, quotas, and error surfaces.
  • Cloudinary for media so app servers aren’t file bottlenecks.

Architecture (high level)

[ Browser (React) ] | v [ API Gateway / Express ] | | \ | | \---> [ Judge0 API ] | | | \---> [ Redis: sessions + cache ] \ \---> [ MongoDB: persistent data ] | v [ Cloudinary: media ]

Trade-offs

Redis vs pure DB sessions — Faster reads; must design TTL + invalidation to avoid stale auth or leaderboard glitches.
External Judge0 — Offloads sandbox security; adds network latency and vendor coupling—mitigate with timeouts, retries, and user-visible progress.
MongoDB — Flexible submission docs; relational purists might model contests differently—chosen for iteration speed and document-shaped payloads.

Impact (what you can ask me about)

I measured roughly 30% better perceived responsiveness after caching and API work—the same figure I put on my resume. In a live conversation I’ll break down what I timed and what I controlled for.

EasFarm — Agricultural E-Commerce

EasFarm on GitHub

Problem

I was building trust between farmers and buyers with chat and blog content. That means bursty writes and read spikes—exactly where an unindexed Mongo path or a chat service fused into the monolith hurts you.

Why I separated concerns

Message threads don’t scale on accidental full scans. Hot blog + chat APIs without caching amplify load. I wanted chat deploys and failures isolated from the core commerce API where possible.

What I implemented

  • Microservice-style chat service to isolate real-time traffic and deployment.
  • Indexing + query restructuring for message and feed paths (~35% query latency reduction, resume).
  • Redis caching on API responses where safe (~30% API response improvement, resume).
  • Integrated blogging for engagement without bolting on a separate CMS prematurely.

Architecture sketch

[ React SPA ] | \ | \--> [ Blog API / content ] v [ Core commerce API ] | \ | \--> [ MongoDB + indexes ] v [ Chat service (µsvc-style) ] | v [ Redis cache layer ]

Trade-offs

Microservice for chat — Independent scale and deploys; operational overhead (logging, tracing) increases—acceptable when chat is a product differentiator.
SQL vs NoSQL — MongoDB fits flexible message/blog documents; reporting-heavy analytics might later want a warehouse—documented as future evolution.
Cache consistency — Redis speeds reads; write-through vs cache-aside chosen per endpoint to limit stale UX on critical paths.

Systems & how I think

If your loop includes a system-design or trade-off discussion, here’s how I communicate: constraints first, then data store choice, then scaling path, then the bottleneck I’d watch.

How I would design…

URL shortener: Use a SQL or NoSQL store with a unique short-key index; redirect path is read-heavy → cache hot URLs in Redis; collision-resistant ID generation (base62). Bottleneck: read QPS → horizontal app servers + cache; DB for durability and analytics async.

Chat system: WebSockets or SSE for delivery; partition messages by room; store in document/row store with time-ordered index; presence in Redis. Bottleneck: fan-out on large rooms → consider channel services / streaming infra at scale.

Rate limiter: Token bucket or sliding window in Redis (atomic counters); I’d rate-limit per IP and per authenticated client id (never ship real secret keys to a browser—those stay on your server). Bottleneck: Redis if every request hits one shard; I’d watch clock skew in distributed checks.

How I solve problems (DSA & backend)

  • I restate constraints and target complexity before I touch code.
  • I sanity-check with brute force, then refactor using patterns (two pointers, sliding window, graphs, DP) when complexity demands it.
  • I state time/space explicitly and only then harden edge cases.
  • On systems questions I name the bottleneck (DB, network, CPU) and the smallest change that buys headroom—index, cache, or batching.

Experiments & playground

Redis on vs off — Measure p95 API latency on a read-heavy route with and without cache; document hit ratio and invalidation rules.

REST vs GraphQL (hypothesis) — For mobile-heavy clients, GraphQL reduces over-fetching; for simple CRUD microservices, REST stays operationally lighter—pick per bounded context.

JWT vs session cookies — JWT scales statelessly but complicates revocation; server sessions simplify kill-switch at cost of store—hybrid patterns for refresh tokens.
